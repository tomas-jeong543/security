RVP4 파이썬 코드 통합 설명본
================================

대상 파일
---------
1. hashfunc(2).py
2. perm1(2).py
3. rvp4_api_hash_resolver_corrected(1).py
4. rvp4_module_hash_resolver(1).py
5. rvp4_permutation(5).py

이 문서는 위 다섯 파일이 각각 무엇을 계산하고, 서로 어떤 순서로 연결되며,
명령줄에서 어떻게 사용하는지를 한 파일로 정리한 설명서다.
코드 자체의 동작은 변경하지 않았으며, 설명은 업로드된 코드에 구현된 내용만을 기준으로 작성했다.


1. 전체 구조
=============

RVP4 분석 도구의 전체 흐름은 다음과 같다.

[실행파일]
    |
    +-- hashfunc(2).py
    |       -> 메모리상 .text 섹션을 재구성
    |       -> textSectionHash 계산
    |
[사용자 이름]
    |
    +-- rvp4_permutation(5).py
            -> 이름 정규화
            -> v298 계산
            -> v330, v334, v419 계산
            -> perm1 생성
            -> textSectionHash가 있으면 perm2 생성
            -> perm1과 perm2를 합성해 최종 VM handler 매핑 계산

[이미 알고 있는 v419]
    |
    +-- perm1(2).py
            -> perm1만 빠르게 계산하고 검증

[IDA에서 발견한 API 해시 상수]
    |
    +-- rvp4_api_hash_resolver_corrected(1).py
            -> Windows DLL의 모든 named export에 RVP4 API 이름 해시 적용
            -> 목표 해시와 일치하는 실제 API 이름 검색

[PEB 순회에서 사용하는 모듈 해시 또는 forwarder]
    |
    +-- rvp4_module_hash_resolver(1).py
            -> DLL 모듈 이름 해시 계산
            -> 이름 또는 ordinal로 export 검색
            -> forwarded export를 재귀적으로 따라가 최종 주소 계산

핵심 관계는 다음 한 줄로 정리할 수 있다.

    이름 -> v419 -> perm1
    v419 + textSectionHash -> perm2
    최종 handler = inverse_perm2[perm1[원본 논리 opcode]]


2. 공통 구현 원칙
=================

2.1 정수 오버플로 재현
----------------------
원본 프로그램은 C/C++의 unsigned 32비트 및 unsigned 64비트 연산을 사용한다.
Python 정수는 자동으로 크기가 확장되므로 각 코드에서는 다음 마스크를 사용한다.

    MASK32 = 0xFFFFFFFF
    MASK64 = 0xFFFFFFFFFFFFFFFF

u32() 또는 u64()를 거치지 않으면 곱셈과 시프트 결과가 원본과 달라질 수 있다.
특히 xorshift, FNV 계열 곱셈, rotate 연산에서는 단계마다 비트 수를 제한해야 한다.

2.2 PE 파일 직접 파싱
--------------------
hashfunc, API resolver, module resolver는 pefile 같은 외부 라이브러리를 사용하지 않는다.
대신 다음 구조를 직접 읽는다.

    DOS Header
      - e_magic = "MZ"
      - e_lfanew = 0x3C 위치의 NT Header 오프셋

    NT Header
      - "PE\0\0" 서명
      - IMAGE_FILE_HEADER
      - IMAGE_OPTIONAL_HEADER
      - Data Directory

    Section Table
      - VirtualSize
      - VirtualAddress
      - SizeOfRawData
      - PointerToRawData

    Export Directory
      - AddressOfFunctions
      - AddressOfNames
      - AddressOfNameOrdinals

이 방식은 설치 의존성이 없고, IDA에서 본 PE 구조와 코드가 직접 대응된다는 장점이 있다.

2.3 rotate와 xorshift
---------------------
API 및 module hash는 32비트 rotate-left 5비트를 사용한다.
이름 상태 및 permutation은 64비트 rotate 또는 xorshift를 사용한다.

    ROL32(value, 5)

    state ^= state << 13
    state ^= state >> 7
    state ^= state << 17

각 단계의 64비트 마스킹이 중요하다.


3. hashfunc(2).py
================

3.1 목적
--------
RVP4 실행파일의 메모리상 .text 섹션을 원본 프로그램과 같은 방식으로 해시한다.
최종 출력값이 textSectionHash다.

이 값은 perm2 seed를 만들 때 사용되므로, 실행파일을 패치했다면 패치된 파일에서 다시 계산해야 한다.
소프트웨어 중단점이 .text 바이트를 0xCC로 바꾸는 경우에도 실행 중 계산값이 달라질 수 있다.

3.2 입력과 출력
---------------
입력:
    분석할 Windows PE 실행파일 경로

주요 출력:
    .text VirtualAddress
    .text VirtualSize
    .text RawOffset
    .text RawSize
    초기 해시
    최종 textSectionHash

기본 사용:

    python "hashfunc(2).py" reversing_project4_output_fixed_v2.exe

기대값과 비교:

    python "hashfunc(2).py" reversing_project4_output_fixed_v2.exe --expected 19F8806B

섹션 목록도 출력:

    python "hashfunc(2).py" reversing_project4_output_fixed_v2.exe --list-sections

각 2바이트 처리 단계 출력:

    python "hashfunc(2).py" reversing_project4_output_fixed_v2.exe --trace

3.3 Section 데이터 구조
-----------------------
Section dataclass는 다음 정보를 저장한다.

    name
    virtual_size
    virtual_address
    raw_size
    raw_offset

parse_sections()가 PE 섹션 테이블을 읽어 Section 목록을 만든다.
그중 이름이 정확히 ".text"인 섹션을 선택한다.

3.4 메모리상 .text 재구성
-------------------------
원본 코드는 디스크의 raw 파일 오프셋이 아니라 다음 주소를 읽는다.

    ImageBaseAddress + .text VirtualAddress

따라서 get_loaded_section_bytes()는 디스크의 .text를 메모리에 로드된 형태로 재구성한다.

    1. PointerToRawData에서 SizeOfRawData만큼 읽는다.
    2. VirtualSize보다 길면 VirtualSize까지만 사용한다.
    3. VirtualSize가 더 크면 남은 영역을 0으로 채운다.

즉 실제 Windows 로더의 섹션 매핑 동작을 필요한 범위에서 재현한다.

3.5 해시 상수
-------------

    INITIAL_HASH = 0xA17C9E3D
    MUL_A        = 73,244,475
    MUL_B        = 785,358,208
    ADD_C        = 2,135,587,861

mix_word(value)는 다음 식을 unsigned 32비트로 계산한다.

    product_a = u32(MUL_A * value)
    shifted   = product_a >> 25
    product_b = u32(MUL_B * value)
    result    = u32(shifted + product_b + ADD_C)

3.6 2바이트 단위 해시 루프
--------------------------
rvp4_text_hash()는 .text를 두 바이트씩 처리한다.

    first_mixed  = current_hash XOR byte0
    second_mixed = mix_word(first_mixed) XOR byte1
    current_hash = mix_word(second_mixed)

VirtualSize가 홀수라면 마지막 1바이트를 별도로 처리한다.

    last_mixed   = current_hash XOR last_byte
    current_hash = mix_word(last_mixed)

3.7 반환 코드
-------------

    0: 정상 완료 또는 --expected 일치
    1: 파일/PE 형식/섹션 오류
    2: --expected 값과 실제 계산값 불일치

3.8 분석 시 주의점
------------------
- 원본 실행파일과 패치된 실행파일은 .text가 다르므로 해시도 달라질 수 있다.
- 소프트웨어 breakpoint는 명령어 첫 바이트를 임시로 0xCC로 바꿀 수 있다.
- 정확한 실행 중 값 검증에는 하드웨어 breakpoint가 더 적합하다.
- --trace는 .text 전체를 출력하므로 결과가 매우 길어질 수 있다.


4. perm1(2).py
==============

4.1 목적
--------
이미 IDA 또는 다른 도구에서 v419 값을 구한 상태에서 첫 번째 opcode permutation인 perm1만 계산한다.
이름 정규화나 v298 계산은 하지 않는 집중형 검증 도구다.

4.2 입력과 출력
---------------
입력:
    64비트 v419 값

예:

    python "perm1(2).py" 0B5860F65C1EC6FC

세부 셔플 과정:

    python "perm1(2).py" 0B5860F65C1EC6FC --trace

역매핑까지 출력:

    python "perm1(2).py" 0B5860F65C1EC6FC --inverse

4.3 seed 생성
-------------

    PERM1_SEED_XOR = 0x64C7920094671459
    initial_state  = v419 XOR PERM1_SEED_XOR

Tomas 사례:

    v419          = 0x0B5860F65C1EC6FC
    initial_state = 0x6F9FF2F6C879D2A5

4.4 초기 opcode 배열
--------------------

    INITIAL_OPCODE_TABLE = [0x00, 0x01, ..., 0x12]

총 19개의 논리 opcode를 순서대로 넣고 셔플한다.

4.5 xorshift64
--------------

    state = u64(state XOR (state << 13))
    state = u64(state XOR (state >> 7))
    state = u64(state XOR (state << 17))

IDA의 중첩 표현을 세 단계로 풀어 쓴 것이다.

4.6 Fisher-Yates 셔플
---------------------
size가 19에서 2까지 감소한다.

    state = xorshift64(state)
    selected_index = state % size
    last_index = size - 1
    swap(table[last_index], table[selected_index])

결과 table이 perm1이다.

Tomas 기준 결과:

    0C 08 11 07 06 0D 09 02 0B 04 03 00 01 10 0F 0E 05 12 0A

4.7 정방향과 역방향
-------------------
정방향:

    perm1[logical_opcode] = encoded_opcode

역방향:

    inverse[encoded_opcode] = logical_opcode

--inverse 옵션은 디버거에서 본 실제 opcode 바이트가 어떤 원래 논리 opcode였는지 찾을 때 유용하다.

4.8 rvp4_permutation과의 차이
-----------------------------
perm1(2).py:
    v419를 직접 입력받아 perm1만 계산한다.

rvp4_permutation(5).py:
    원본 이름부터 v419, perm1, perm2, 최종 handler 매핑까지 계산한다.

따라서 v419 자체를 검증할 때는 두 파일의 결과를 비교할 수 있다.


5. rvp4_api_hash_resolver_corrected(1).py
=========================================

5.1 목적
--------
IDA에서 발견한 32비트 API 해시 상수를 실제 Windows API 이름으로 복원한다.

이 코드는 해시를 수학적으로 역산하지 않는다.
지정된 DLL의 모든 named export를 열거하고 각 이름에 같은 해시 함수를 적용한 다음,
목표 해시와 일치하는 후보를 찾는다.

5.2 기본 대상 DLL
-----------------
Windows에서 --dll을 지정하지 않으면 다음 파일을 검사한다.

    kernel32.dll
    kernelbase.dll
    ntdll.dll
    advapi32.dll
    user32.dll
    win32u.dll

Windows가 아닌 환경에서는 기본 DLL 경로가 없으므로 --dll로 파일을 직접 지정해야 한다.

5.3 API 이름 해시 상수
----------------------

    FNV_OFFSET_BASIS_32 = 0x811C9DC5
    FNV_PRIME_32        = 0x01000193
    HASH_XOR_CONSTANT   = 0x9E3779B9

5.4 이름 정규화
---------------
- ASCII 이름만 허용한다.
- A-Z는 a-z로 변환한다.
- 문자열 길이의 짝수 부분은 2문자씩 처리한다.
- 홀수 길이라면 마지막 문자를 별도로 처리한다.

5.5 두 문자 단위 해시
----------------------
문자 쌍 c0, c1에 대해:

    pair_step = ROL32(
        FNV_PRIME_32 * (state XOR lower(c0)),
        5
    )

    pair_out = ROL32(
        FNV_PRIME_32 * (pair_step XOR lower(c1) XOR HASH_XOR_CONSTANT),
        5
    )

    state = pair_out XOR HASH_XOR_CONSTANT

문자열 길이가 짝수이면 비교값은 마지막 pair_out이다.
문자열 길이가 홀수이면 마지막 문자에 대해 다음을 계산한다.

    result = ROL32(
        FNV_PRIME_32 * (state XOR lower(last)),
        5
    )

일반적인 문자별 FNV 반복과 같다고 단순화하면 결과가 달라질 수 있다.

검증 예:

    python "rvp4_api_hash_resolver_corrected(1).py" --name GetStdHandle

코드 실행 결과:

    GetStdHandle -> 0x7A130126

5.6 Export Directory 열거
-------------------------
PEImage.enumerate_named_exports()는 다음 순서로 export를 읽는다.

    AddressOfNames[name_index] -> name RVA
    AddressOfNameOrdinals[name_index] -> ordinal index
    AddressOfFunctions[ordinal index] -> function RVA

출력에 포함되는 정보:

    DLL 이름
    API 이름
    계산된 해시
    ordinal
    function RVA
    forwarder 문자열

5.7 forwarded export 판정
-------------------------
function RVA가 Export Directory 범위 안에 있으면 코드 주소가 아니라 forwarder 문자열로 판단한다.
예:

    KERNELBASE.Sleep
    NTDLL.RtlSomething

이 API resolver는 forwarder 문자열을 표시하지만 다른 DLL로 재귀 해석하지는 않는다.
재귀적으로 최종 대상을 따라가는 기능은 module resolver에 있다.

5.8 사용 방법
-------------
특정 해시 검색:

    python "rvp4_api_hash_resolver_corrected(1).py" 0x7A130126

여러 해시 검색:

    python "rvp4_api_hash_resolver_corrected(1).py" 0x7A130126 0xE424789F

알려진 API 이름의 해시 계산:

    python "rvp4_api_hash_resolver_corrected(1).py" --name GetStdHandle

텍스트 파일에서 해시 목록 읽기:

    python "rvp4_api_hash_resolver_corrected(1).py" --hash-file hashes.txt

특정 DLL만 검사:

    python "rvp4_api_hash_resolver_corrected(1).py" 0x7A130126 --dll C:\Windows\System32\kernel32.dll

전체 export와 해시 덤프:

    python "rvp4_api_hash_resolver_corrected(1).py" --dump-common

5.9 결과 해석
-------------
예상 형식:

    0x7A130126 -> kernel32.dll!GetStdHandle
      path       : C:\Windows\System32\kernel32.dll
      ordinal    : ...
      RVA        : 0x........
      forwarder  : KERNELBASE.GetStdHandle

같은 해시가 여러 DLL 또는 여러 export 이름에서 충돌할 수 있으므로 모든 match를 확인해야 한다.

5.10 제한사항
-------------
- named export만 후보로 사용한다.
- API 이름이 비 ASCII라면 건너뛴다.
- DLL 파일의 버전에 따라 export 목록, ordinal, forwarder가 달라질 수 있다.
- 목표 API가 검사 대상 DLL에 없으면 NOT FOUND가 나온다.
- hash collision이 존재할 수 있으므로 모듈과 호출 맥락을 함께 확인해야 한다.


6. rvp4_module_hash_resolver(1).py
=================================

6.1 목적
--------
RVP4의 PEB 기반 모듈 순회와 Export resolver 동작을 별도 도구로 재현한다.

주요 기능:

    1. DLL 모듈 이름 해시 계산
    2. 모듈 해시로 DLL 파일 검색
    3. export 이름 또는 ordinal 검색
    4. forwarded export 재귀 해석
    5. 최종 function RVA와 static VA 출력

6.2 모듈 이름 해시
------------------
초기값과 상수:

    state               = 0x811C9DC5
    FNV_PRIME_32        = 0x01000193
    HASH_XOR_CONSTANT   = 0x9E3779B9

각 문자에 대해:

    1. 첫 번째 '.'을 만나면 종료
    2. A-Z를 a-z로 변환
    3. state = ROL32(((state XOR ch) * FNV_PRIME_32), 5)
    4. state = state XOR HASH_XOR_CONSTANT

따라서 다음 이름은 같은 해시를 만든다.

    kernel32
    kernel32.dll
    KERNEL32.DLL

검증 예:

    python "rvp4_module_hash_resolver(1).py" hash kernel32.dll

코드 실행 결과:

    0xCFDCAD2E

6.3 export 검색 방식
--------------------
이름 검색:

    function_rva_by_name("GetStdHandle")

ordinal 검색:

    function_rva_by_ordinal(123)

명령줄에서는 ordinal을 #123 형식으로 입력한다.

6.4 forwarded export 재귀 처리
------------------------------
function RVA가 Export Directory 내부에 있으면 forwarder 문자열로 읽는다.

예:

    KERNELBASE.Sleep
    NTDLL.#123

module token과 symbol을 분리한 뒤 대상 모듈을 다시 찾고 export를 재귀적으로 해석한다.

코드의 재귀 제한은 원본 디컴파일 흐름을 반영한다.

    초기 depth_counter = 0
    named forwarder를 따라갈 때 +2
    next_depth > 4이면 중단

따라서 무한 forwarder 체인을 방지한다.

6.5 ModuleRepository
--------------------
ModuleRepository는 DLL 파일을 검색하고 캐시한다.

주요 동작:

    - search_directories를 순회
    - 확장자 .dll, .exe, .sys, .ocx, .cpl만 후보로 사용
    - 파일 이름에 module_name_hash() 적용
    - wanted_hash와 같으면 PEImage 로드
    - 이미 읽은 경로와 이미지 객체를 캐시

기본 scan_limit는 64다.
이는 디컴파일된 모듈 순회가 무한히 진행되지 않도록 제한한 구조와 대응한다.

6.6 API-set 제한
----------------
forwarder가 다음과 같은 API-set 이름을 가리킬 수 있다.

    api-ms-win-...
    ext-ms-win-...

이 코드는 Windows PEB의 ApiSetMap 스키마를 에뮬레이션하지 않는다.
따라서 일반 파일로 찾을 수 없는 API-set forwarder는 오류로 보고한다.

6.7 사용 방법
-------------
모듈 해시 계산:

    python "rvp4_module_hash_resolver(1).py" hash kernel32.dll

특정 PE에서 export 이름 해석:

    python "rvp4_module_hash_resolver(1).py" resolve-path C:\Windows\System32\kernel32.dll GetStdHandle

ordinal 해석:

    python "rvp4_module_hash_resolver(1).py" resolve-path C:\Windows\System32\ntdll.dll "#123"

모듈 해시로 파일을 찾은 뒤 export 해석:

    python "rvp4_module_hash_resolver(1).py" resolve-hash 0xCFDCAD2E GetStdHandle

검색 폴더 추가:

    python "rvp4_module_hash_resolver(1).py" resolve-hash 0xCFDCAD2E GetStdHandle --search-dir D:\dlls

검색 제한 변경:

    python "rvp4_module_hash_resolver(1).py" resolve-hash 0xCFDCAD2E GetStdHandle --scan-limit 256

6.8 출력값
----------

    module_path
    module_hash
    query
    ordinal
    function_rva
    image_base
    static_va
    forward_chain

static_va는 PE Optional Header의 ImageBase와 function RVA를 더한 값이다.
이는 실제 ASLR 적용 후 런타임 주소가 아니라 파일의 선호 ImageBase 기준 주소다.

6.9 API resolver와 차이
-----------------------
API hash resolver:
    32비트 API 이름 해시 -> export 이름 후보를 찾는다.

module resolver:
    모듈 이름 해시 또는 모듈 경로 + 정확한 symbol -> 실제 export RVA를 찾는다.
    forwarded export도 재귀적으로 따라간다.

실전에서는 API hash resolver로 함수 이름을 복원한 뒤,
module resolver로 해당 DLL의 최종 RVA와 forwarder 체인을 확인할 수 있다.


7. rvp4_permutation(5).py
=========================

7.1 목적
--------
RVP4의 이름 기반 상태 계산과 두 permutation 및 최종 opcode 매핑을 한 파일에서 처리한다.
다섯 코드 중 가장 통합적인 도구다.

구현 범위:

    이름 정규화
    v298 계산
    v330 계산
    v334 계산
    v419 계산
    perm1 seed 및 perm1
    perm2 seed 및 perm2
    inverse perm2
    최종 VM handler 매핑
    Tomas 자체 검증

7.2 이름 정규화
---------------
normalize_name()은 원본 입력 루틴을 다음 규칙으로 재현한다.

    - ASCII만 허용
    - 앞뒤의 일반 공백 0x20 제거
    - 연속 공백을 하나로 축약
    - A-Z를 a-z로 변환
    - 허용 범위는 출력 가능한 ASCII 0x20~0x7E
    - 정규화 후 길이는 3~24바이트

주의:
    탭은 일반 공백으로 취급하지 않는다.
    Python str.strip() 전체가 아니라 raw.strip(b" ")를 사용해 일반 공백만 제거한다.

예:

    "John  Smith" -> "john smith"
    " Tomas "     -> "tomas"

7.3 이름 해시 초기값과 상수
---------------------------

    NAME_HASH_INITIAL = 0xCBF29CE484222325
    NAME_HASH_PRIME   = 0x100000001B3

각 이름 바이트에 대해 update_name_hash()를 적용한다.

    multiplied = u64(NAME_HASH_PRIME * (current_hash XOR byte))
    new_hash   = u64(multiplied XOR ROL64(multiplied, 23))

IDA의 다음 최적화 식을 rotate-left 23으로 정리한 것이다.

    (0x80000000D9800000 * x) | (t >> 41)

7.4 v298
--------
정규화된 이름의 각 바이트를 순서대로 update_name_hash()에 넣은 최종 64비트 상태다.

Tomas:

    normalized = "tomas"
    v298       = 0x59EF5B620806E136

7.5 v330, v334, v419
--------------------

    v330 = u64(v298 XOR (v298 >> 29))

    v334 = u64(
        0x9E3779B185EBCA87 * v330
    )

    v419 = u64(v334 XOR (v334 >> 32))

Tomas:

    v330 = 0x59EF5B60C77C3A26
    v334 = 0x0B5860F65746A60A
    v419 = 0x0B5860F65C1EC6FC

v419가 이름에 따라 perm1을 바꾸는 핵심 상태다.

7.6 perm1
---------

    perm1_seed = v419 XOR 0x64C7920094671459
    perm1      = shuffle_opcode_table(perm1_seed)

셔플 알고리즘은 perm1(2).py와 동일한 xorshift64 + Fisher-Yates다.

7.7 perm2
---------
perm2에는 textSectionHash가 추가로 필요하다.

    v355 = v419 XOR (textSectionHash << 32)

    perm2_seed = v355 XOR 0x53A9D1E794671459

    perm2 = shuffle_opcode_table(perm2_seed)

즉 perm2는 이름뿐 아니라 실행파일의 .text 상태에도 결합된다.

명령줄에서는 --text-hash를 지정하면 자동으로 계산된다.
활성화하거나 주석 해제할 함수는 없다.

    python "rvp4_permutation(5).py" Tomas --text-hash 19F8806B

7.8 inverse permutation
-----------------------

    permutation[logical] = encoded

이면:

    inverse[encoded] = logical

perm2는 배열 인덱스가 VM dispatch handler 번호이고 배열 값이 비교되는 encoded opcode다.
따라서 encoded opcode X를 읽었을 때 실행되는 handler는 다음과 같다.

    handler = inverse_perm2[X]

7.9 최종 opcode 매핑
--------------------
원본 논리 opcode가 먼저 perm1로 인코딩되고,
VM dispatch에서 그 encoded opcode를 perm2의 어느 위치에서 찾는지 결정한다.

    encoded_opcode = perm1[original_opcode]
    final_handler  = inverse_perm2[encoded_opcode]

최종 공식:

    final_handler[original_opcode]
        = inverse_perm2[perm1[original_opcode]]

--final-map 옵션:

    python "rvp4_permutation(5).py" Tomas --text-hash 19F8806B --final-map

중요:
    출력되는 handler 0x00~0x12는 handler 인덱스다.
    아직 ADD, XOR, CMP, MOV_IMM64 같은 명령 의미를 자동으로 붙인 것은 아니다.
    각 handler의 실제 동작은 디컴파일된 분기와 VM 상태 변경을 별도로 분석해야 한다.

7.10 Tomas 검증값
-----------------
다음 명령:

    python "rvp4_permutation(5).py" Tomas --text-hash 19F8806B --final-map

주요 결과:

    정규화 이름    : tomas
    v298            : 0x59EF5B620806E136
    v330            : 0x59EF5B60C77C3A26
    v334            : 0x0B5860F65746A60A
    v419            : 0x0B5860F65C1EC6FC
    perm1 seed      : 0x6F9FF2F6C879D2A5
    perm1           : 0C 08 11 07 06 0D 09 02 0B 04 03 00 01 10 0F 0E 05 12 0A

    v355            : 0x12A0E09D5C1EC6FC
    perm2 seed      : 0x4109317AC879D2A5
    perm2           : 08 07 0A 0F 12 0B 05 09 04 03 11 01 06 10 02 0E 0D 00 0C

7.11 자체 검증
---------------

    python "rvp4_permutation(5).py" --self-test

run_self_test()는 Tomas의 v419가 다음 값과 일치하는지 확인한다.

    0x0B5860F65C1EC6FC

이 검증은 이름 정규화, v298, v330, v334, v419 계산 경로가 기준 사례와 맞는지 확인한다.
perm2나 모든 최종 handler 동작까지 검증하는 것은 아니다.

7.12 주요 함수별 역할
---------------------

    normalize_name(name)
        원본 입력과 같은 이름 정규화

    update_name_hash(current_hash, byte)
        이름 한 바이트를 v298 상태에 반영

    calculate_v298(normalized_name)
        정규화된 전체 이름의 v298 계산

    derive_v419(v298)
        v330, v334, v419 반환

    xorshift64(state)
        permutation PRNG 상태 갱신

    shuffle_opcode_table(seed)
        19개 opcode Fisher-Yates 셔플

    generate_perm1_from_name(name)
        이름부터 v419와 perm1까지 계산

    generate_perm2_seed(v419, text_section_hash)
        perm2 초기 seed 계산

    generate_perm2(v419, text_section_hash)
        perm2 배열 계산

    invert_permutation(permutation)
        encoded 값에서 배열 인덱스로 가는 역표 생성

    compose_final_opcode_mapping(perm1, perm2)
        원본 논리 opcode에서 최종 handler 인덱스로 가는 표 생성


8. 권장 사용 순서
=================

8.1 1단계: 실제 .text 해시 계산
------------------------------

    python "hashfunc(2).py" reversing_project4_output_fixed_v2.exe --expected 19F8806B

패치할 때마다 다시 계산하는 것이 안전하다.

8.2 2단계: 이름 기반 permutation 계산
-------------------------------------

    python "rvp4_permutation(5).py" "John Smith" --text-hash 19F8806B --final-map

이 단계에서 다음을 한 번에 얻는다.

    normalizedName
    v298
    v330
    v334
    v419
    perm1
    perm2
    inverse perm2
    final handler mapping

8.3 3단계: v419만 별도 검증
--------------------------

    python "perm1(2).py" <rvp4_permutation에서 나온 v419> --inverse

두 스크립트의 perm1이 같아야 한다.

8.4 4단계: API 해시 복원
------------------------
IDA에서 확인한 API 해시 상수를 넣는다.

    python "rvp4_api_hash_resolver_corrected(1).py" 0x7A130126

직접 이름 해시를 확인하려면:

    python "rvp4_api_hash_resolver_corrected(1).py" --name GetStdHandle

8.5 5단계: 모듈/forwarder 검증
-----------------------------

    python "rvp4_module_hash_resolver(1).py" hash kernel32.dll

    python "rvp4_module_hash_resolver(1).py" resolve-path C:\Windows\System32\kernel32.dll GetStdHandle

forwarder가 있다면 최종 대상 DLL과 함수까지 chain을 출력한다.

8.6 6단계: x64dbg와 비교
-----------------------
- perm1은 셔플 완료 직후의 19바이트 배열과 비교한다.
- perm2는 두 번째 셔플 완료 직후 배열과 비교한다.
- .text 해시는 소프트웨어 breakpoint를 제거한 상태에서 하드웨어 breakpoint로 비교한다.
- final mapping의 handler 번호는 dispatch if 체인의 순서와 비교한다.


9. 파일별 선택 기준
===================

상황: 실행파일의 .text 해시가 필요하다.
사용: hashfunc(2).py

상황: v419는 이미 알고 있고 perm1만 빠르게 확인하고 싶다.
사용: perm1(2).py

상황: IDA에 0x12345678 같은 API 해시 상수가 보인다.
사용: rvp4_api_hash_resolver_corrected(1).py

상황: kernel32.dll 같은 모듈 해시를 확인하거나 forwarded export 최종 주소가 필요하다.
사용: rvp4_module_hash_resolver(1).py

상황: 이름부터 perm1, perm2, 최종 handler 매핑까지 전부 계산하고 싶다.
사용: rvp4_permutation(5).py


10. 검증 상태와 주의사항
========================

업로드된 다섯 Python 파일은 Python 문법 컴파일 검사를 통과했다.

    python -m py_compile ...

또한 다음 코드 내부 검증을 실행했다.

    rvp4_permutation(5).py --self-test
        -> Tomas의 v419 기준값 일치

    perm1(2).py 0B5860F65C1EC6FC
        -> Tomas perm1 계산

    rvp4_module_hash_resolver(1).py hash kernel32.dll
        -> 0xCFDCAD2E

    rvp4_api_hash_resolver_corrected(1).py --name GetStdHandle
        -> 0x7A130126

현재 업로드에는 실제 분석 대상 EXE와 Windows DLL 파일이 포함되지 않았으므로,
hashfunc의 특정 실행파일 최종 해시와 API/module resolver의 실제 DLL export 검색은 이 설명본 제작 과정에서 새로 재실행하지 않았다.
해당 부분은 사용자의 Windows 환경에 있는 실제 파일을 대상으로 실행해야 한다.


11. 핵심 요약
=============

- hashfunc는 실행파일 상태를 textSectionHash로 만든다.
- rvp4_permutation은 이름 상태를 v419로 만들고 perm1을 계산한다.
- v419와 textSectionHash를 결합하면 perm2가 만들어진다.
- 최종 VM handler는 inverse_perm2[perm1[opcode]]로 계산한다.
- perm1.py는 v419부터 시작하는 독립 검증 도구다.
- API resolver는 API 이름 해시를 실제 export 이름과 대조한다.
- module resolver는 모듈 해시, 이름/ordinal export, forwarded export 체인을 처리한다.
- 최종 handler 번호는 명령 이름이 아니며, 각 분기의 실제 동작 분석이 추가로 필요하다.
