# EASILE 서버 확장

## 입력 자료

[루트 규칙](../../../AGENTS.md), 사용자가 승인한 마일스톤·파일·범위, [문서 색인](../../../docs/server-extension/README.md), 해당 단계의 아키텍처·프로토콜·검증 계획.

## 절차

1. [개발 계획](../../../docs/server-extension/implementation-plan.md)의 선행 조건과 현재 승인을 확인한다. 현재 문서 초안 작성 승인을 M0 실행이나 M2 구현 승인으로 확대하지 않는다.
2. 새 판단은 확인 사실·설계 제안·TBD로 나눈다. 필요한 사람 결정이 없으면 관련 구현은 진행하지 않고 독립적으로 가능한 승인 작업만 한다.
3. 플레이어 입력 의도와 서버 소유 봇 발사를 구분한다. 서버가 스스로 만든 상태·시간·방향·투사체 ID로 검증하도록 한다. 클라이언트 해시·최종 발사 보고를 정답으로 삼지 않는다.
4. 초기에는 제한된 발사 검증 상태와 접속 경계를 설계한다. 전체 GameCore 분리는 비교 후보이며 초기 필수 작업으로 확대하지 않는다.
5. HK-01 방향·쿨다운·생성 검증에서 필요한 서버 상태, 거절·승인 시점, 클라이언트 표시 한계를 명시한다. 서버 상태가 부족하면 검증 가능하다고 단정하지 않는다.
6. 승인된 구현 시에도 기존 UI·렌더·입력·방어·실험 파일을 보존하고, 변경 대상과 보존할 호출을 diff로 검토한다. 프로토콜·연결 실패·지연·중복·재연결 검증을 포함한다.
7. 단계 산출물과 실제 증거를 정리하고 정해진 사람 검토 시점에서 다음 단계로의 명시적 승인을 기다린다.

## 산출물

승인 범위 내 설계 또는 구현 diff, 변경 결정·TBD, 보안 보존 표, 검증 증거, 다음 단계 사람 검토 자료.

## 완료 기준

승인된 단계의 완료 조건과 증거가 충족돼야 한다. 미해결 TBD가 완료 조건에 영향을 주면 그 단계는 미완료다. 같은 PC의 서버 격리를 신뢰 실행 환경이나 완전한 안티치트로 표현하지 않는다.
