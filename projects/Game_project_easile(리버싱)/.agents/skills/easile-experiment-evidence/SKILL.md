# EASILE 실험 증거 관리

## 입력 자료

[루트 규칙](../../../AGENTS.md), 승인된 실험 조건, 원본 소스·바이너리·보고서·로그, [조사 기록](../../../docs/server-extension/repository-audit.md), [비교 검증 계획](../../../docs/server-extension/validation-plan.md).

## 절차

1. 새 실행 ID와 독립 출력 경로를 정한다. 원본의 경로·SHA-256·CWD·시각·빌드 설정·소스 대응의 확인 수준을 기록한다. 파일 해시는 동일성 식별이며 클라이언트 신뢰 증거가 아니다.
2. 실제 공격 필터와 DLLGuard 원본 호출 여부를 소스로 조사한다. README·주석·과거 결과와 다르면 양쪽 근거와 차이를 보존한다.
3. 조건을 무주입, 방어 활성 공격, DLLGuard 우회 공격, 서버 관측, 서버 강제 적용 등으로 분리한다. 조건 간 결과를 합치지 않는다.
4. 실행 승인이 있는 범위에서만 수집한다. 로드·설치·detour 호출·최종 생성·실제 효과·탐지·경고·종료를 각각 판정한다. 프로세스 생존과 설치 로그만으로 플레이 성공을 쓰지 않는다.
5. 실험자 직접 확인은 출처를 붙여 인정하고, 호출별 계측·자동 검증과 구분한다. 각도 실측은 같은 이벤트의 입력·출력 벡터, 원본 전달 및 최종 투사체와의 연결이 있어야 한다.
6. 새 문서에 근거 파일·구간·해시·한계를 기록한다. 없는 증거 경로는 누락으로 남기고 보고서 문구로 대체하지 않는다.

## 산출물

조건별 실험표, 증거 목록, 단계별 판정, 미검증·누락 목록, 원본 보존 및 Git diff 기록. 결과는 [검증 계획의 증거 형식](../../../docs/server-extension/validation-plan.md)에 맞춘다.

## 완료 기준

제3자가 어떤 파일·방어 조건·관측에서 결론이 나왔는지 추적할 수 있어야 한다. 실행하지 않은 단계와 실패한 실험을 숨기지 않는다. 효과 확인, 정확한 각도 실측, 방어 활성 상태의 효과를 같은 판정으로 취급하지 않는다.
