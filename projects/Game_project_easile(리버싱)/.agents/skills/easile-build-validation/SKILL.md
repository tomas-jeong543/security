# EASILE 빌드 검증

## 입력 자료

- [루트 규칙](../../../AGENTS.md), 승인된 변경 범위와 마일스톤.
- [저장소 조사](../../../docs/server-extension/repository-audit.md), [검증 계획](../../../docs/server-extension/validation-plan.md).
- 실제 솔루션·프로젝트 설정, 작업 전 Git 상태, 보존 대상 EXE/PDB·로그 식별값.

## 절차

1. Git 최상위와 프로젝트 경로를 확인하고 프로젝트 범위 diff·미추적 파일을 기록한다. 기존 사용자 변경은 보존한다.
2. 문서 검토인지 실행 검증인지 구분한다. 문서 작업은 링크·메타데이터·diff만 검사할 수 있으며 게임 검증을 미실행으로 명시한다.
3. 빌드가 승인된 경우 기존 산출물·로그를 덮기 전에 별도 증거 경로에 식별·보존한다. 구성과 툴체인, 정확한 명령·CWD를 기록한다.
4. 승인된 Debug/Release x64를 빌드한다. 실패 시 후속 게임 테스트를 통과 처리하지 않고 원인을 기록한다. 새 경고도 기존 경고와 구분한다.
5. 승인된 테스트 EXE를 실행하고 종료 코드, 항목별 결과, 실제 실행 수를 수집한다. `49개 등록`은 `49개 통과`가 아니다. UI·시각 검사는 별도 승인 범위와 실행 증거가 필요하다.
6. 테스트 EXE의 고정 RVA 검사 문제, CWD 공용 로그 오염, GUI 모달·타임아웃은 제품 결함과 실행 환경 문제로 나눠 조사한다. 실패를 숨기기 위한 테스트 수정은 금지한다.
7. 작업 후 diff·공백 검사·보존 여부를 확인하고 실행 및 미실행 목록을 보고한다.

## 산출물

실행 ID별 명령·환경·종료 코드·로그·파일 해시·diff 목록, 실패와 제한 사항. 기존 `tools/validate_v014.ps1`은 출력 파일을 변경하므로 내용을 확인하고 승인 범위 내에서만 사용한다.

## 완료 기준

승인된 검증이 끝나고 모든 실패·미실행이 드러나야 한다. 실패가 있으면 검증 작업은 보고할 수 있지만 제품 PASS나 마일스톤 완료로 선언하지 않는다. 기존 증거가 보존되고 새 파일 diff도 검토됐어야 한다.
