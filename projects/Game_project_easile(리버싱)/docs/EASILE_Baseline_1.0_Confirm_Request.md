# EASILE 2D Anti-Cheat Game — Baseline 1.0 공식 확정 지시

## 1. 목적

현재 게임은 구현과 자동 검증뿐 아니라,
**사용자가 직접 실제 플레이를 수행하여 게임 동작과 플레이 감각을 확인한 상태**이다.

사용자는 현재 게임 상태에 만족하며,
이 버전을 이후 보안 실험의 기준이 되는 **Baseline 1.0**으로 공식 확정하려고 한다.

따라서 기존 문서에서 사용한 다음과 같은 표현은 더 이상 사용하지 마라.

- Baseline 1.0 후보
- NEW BASELINE: NOT READY
- 공식 baseline 미확정
- 사용자 직접 플레이 검증 필요

이번 작업의 목적은 현재 상태를
**정식 Baseline 1.0으로 선언하고 기록하는 것**이다.

---

## 2. 사용자 직접 플레이 검증 반영

Baseline 판정에는 다음 사실을 반드시 반영해라.

- 사용자가 직접 게임을 실행했다.
- 사용자가 직접 캐릭터 이동, 전투, 스킬 사용 및 전체적인 플레이 흐름을 확인했다.
- 사용자가 현재 구현 상태를 이후 Patch / DLL Injection / Hooking 실험의 기준으로 사용하기에 충분하다고 판단했다.
- 따라서 사람 직접 플레이 검증을 더 이상 Baseline 확정의 미완 항목으로 기록하지 않는다.

자동 테스트와 별도로,
**사용자 직접 플레이 확인 자체를 Baseline 승인 조건으로 포함**한다.

단,
사용자가 구체적으로 말하지 않은 플레이 결과를 임의로 추가하지 마라.

---

## 3. Baseline 1.0 공식 확정

현재 작업 트리를 이후 모든 보안 실험의 기준인

```text
EASILE Baseline 1.0
```

으로 공식 지정해라.

이후 문서에서는 다음 표현을 사용한다.

```text
Baseline Status: CONFIRMED
Baseline Version: 1.0
```

또는 이에 준하는 명확한 표현을 사용한다.

---

## 4. 기존 문서 수정

현재 프로젝트의 관련 문서를 확인하고,
Baseline이 아직 후보 상태라고 적힌 부분을 수정해라.

특히 다음 종류의 표현을 찾아 정리한다.

```text
Baseline 1.0 후보
NEW BASELINE: NOT READY
공식 baseline 미확정
사람 직접 플레이 검증 필요
```

이를 현재 상태에 맞게 변경한다.

예:

```text
Baseline 1.0 — CONFIRMED
```

---

## 5. Baseline 기록

가능하면 다음 정보를 함께 기록한다.

- Baseline 버전: 1.0
- 확정일
- Debug 빌드 상태
- Release 빌드 상태
- 자동 테스트 상태
- 사용자 직접 플레이 확인 여부
- 이후 첫 보안 실험

첫 보안 실험은 다음으로 예정한다.

```text
Ultimate Cooldown Patch
10 seconds -> 1 second
```

---

## 6. 중요한 원칙

이번 작업에서는 게임 기능을 새로 추가하거나
게임 밸런스를 임의로 수정하지 마라.

또한 아래 작업도 수행하지 마라.

- 실제 EXE 패치
- Ultimate cooldown 변경
- DLL Injection
- Hooking
- Anti-Cheat 방어 코드 작성

이번 작업은 오직

```text
현재 게임을 Baseline 1.0으로 공식 확정하고
관련 문서의 상태를 일관되게 수정하는 작업
```

이다.

---

## 7. 완료 보고

작업 완료 후 다음을 보고해라.

```text
1. Baseline 1.0 공식 확정 여부
2. 수정한 문서 목록
3. 기존 후보/미확정 표현을 수정한 위치
4. Debug/Release 및 기존 테스트 상태
5. 사용자 직접 플레이 확인을 어떻게 기록했는지
6. 다음 실험이 Ultimate Cooldown 10s -> 1s Patch임을 기록했는지
```

현재 게임 상태를 더 이상 후보 상태로 취급하지 말고,
**사용자의 직접 플레이 승인까지 반영된 공식 Baseline 1.0**으로 취급해라.
