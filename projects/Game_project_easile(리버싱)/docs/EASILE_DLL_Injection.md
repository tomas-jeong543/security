# EASILE DLL Injection 실험 후보 분석 지시서 (Codex용)

## 1. 목적

현재 EASILE 2D 게임 프로젝트에서 **DLL Injection을 활용해 동작 변화를 관찰할 수 있는 실험 후보**를 찾아 비교하고, 첫 번째 실험 대상으로 가장 적합한 후보를 추천한다.

이번 작업은 **분석 및 후보 선정만** 수행한다. DLL, 인젝터, 후킹 코드, 우회 코드 등을 **작성하거나 게임 소스코드를 수정하지 않는다**.

## 2. 프로젝트 배경

- Windows x64 / Visual Studio 2022 / C++ / DirectX 11 기반의 로컬 2D 게임이다.
- 게임은 현재 단일 프로세스 구조이며, 외부 네트워크 서버를 사용하지 않는다.
- 플레이어 이동, 기본 공격, 궁극기(J), 체력·회복, 봇 AI, 투사체, 렌더링 등의 기능이 있다.
- 이전 실험(PATCH01)은 **궁극기 쿨타임 변경**과 **CRC32 기반 코드 무결성 검사 및 런타임 검증**을 다루었다.
- DLL Injection 실험은 PATCH01과 구별되는 공격면을 중심으로 설계하되, 기존 방어와의 연관성도 함께 평가한다.
- 작업 범위는 **본인이 소유·개발한 EASILE 게임 실행 파일과 소스코드**로 한정한다. 외부 게임, 타사 프로세스, 안티치트 제품은 대상이 아니다.

> 위 배경은 안내용이다. 실제 구현·파일명·함수명·방어 적용 범위는 **현재 저장소의 소스코드를 직접 확인해 검증**하라. 일치하지 않으면 현재 코드를 우선한다.

## 3. 분석 범위

저장소를 읽고 다음 항목을 파악하라.

1. 진입점, 게임 루프, 프레임 업데이트 흐름 (`main`, `Application`, `GameWorld` 등 실제 구현 기준)
2. 입력 처리와 플레이어 액션 호출 경로 (`InputManager`, 기본 공격, 궁극기)
3. 플레이어·봇의 HP, 이동 속도, 투사체, 피해량, 회복 및 쿨타임을 관리하는 자료구조와 함수
4. 렌더링·HUD 갱신 흐름과 게임 내부 값이 화면에 반영되는 위치
5. 현재 존재하는 무결성 검사 및 런타임 방어의 호출 위치, 검사 대상, 적용 범위
6. Debug/Release 빌드의 차이 및 실험 시 재현성에 영향을 미치는 요소

후보를 선정할 때는 **실제 코드의 파일 경로, 함수·클래스명, 코드 위치(가능하면 행 번호)**를 근거로 제시하라. 저장소에 없는 함수나 변수를 임의로 가정하지 말라.

## 4. 후보 발굴 기준

다음 유형을 참고하되 코드에 근거한 후보를 **최소 5개** 제시한다.

- 플레이어 또는 봇의 HP·회복량 관련 런타임 데이터 변화
- 이동 속도 또는 이동 가능 여부의 런타임 변화
- 기본 공격의 피해량·발사 관련 동작 변화
- 투사체 속도·방향·수명 관련 변화
- 게임 내 정보 표시(HUD) 또는 상태 시각화 변화
- 궁극기 동작·쿨타임 변화 (이전 PATCH01과 중복된다는 단점도 평가)
- 소스코드 분석 중 발견한 더 적합한 후보

**단순 데이터 변경, DLL에 의한 함수 호출 개입, 코드 패치가 서로 다른 실험 방식임을 구분**하라. 특히 DLL을 로드하는 행위만으로 기능 변화가 일어나는 것은 아니므로, 각 후보가 어떤 종류의 관찰·개입을 요구하는지 개념 수준에서 명시하라.

## 5. 후보 평가표

다음 기준으로 각 후보를 1~5점(5점이 더 적합함)으로 평가한다.

| 평가 기준 | 뜻 |
|---|---|
| 구현 난이도 | 첫 실험에서 구현하기 쉬운 정도 (쉬울수록 고득점) |
| 동작 관찰성 | 게임 화면·로그·테스트로 결과가 명확히 드러나는 정도 |
| 재현성 | 여러 번 동일 조건으로 반복할 수 있는 정도 |
| 안전성·복구성 | 크래시·세이브 손상·광범위한 수정 위험이 적고 원상 복구하기 쉬운 정도 |
| 학습 효과 | DLL 로드, 프로세스 내 실행, 메모리 상태 변화 등을 이해하는 데 도움이 되는 정도 |
| 기존 PATCH01과 차별성 | 기존 궁극기 코드 패치 실험과 구별되는 정도 |
| 방어 실험 확장성 | 후속 탐지·검증 실험으로 발전시키기 쉬운 정도 |

모든 기준을 동일 가중치로 합산하여 총점(35점 만점)을 계산한다. 점수의 이유를 짧게 제시하고, 점수가 높은 후보만이 아니라 **실험 목적과 맞는 후보**를 우선 추천하라.

## 6. Codex 출력 형식

### A. 현재 코드 구조 요약

- 핵심 파일과 역할: 5~10줄
- 기존 무결성 검사 범위 및 DLL 실험과의 관계: 3~5줄

### B. 후보 비교표

| 순위 | 후보 기능 | 실제 파일/함수(행 번호) | 관찰할 변화 | 예상 개입 유형 | 난이도 | 관찰성 | 재현성 | 안전성 | 학습 효과 | 차별성 | 방어 확장성 | 합계 |
|---|---|---|---|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | ... | ... | ... | ... | ... | ... | ... | ... | ... | ... | ... | ... |

### C. 최종 추천 TOP 3

각 후보에 대해 다음을 간단히 작성한다.

- 추천 이유와 기존 PATCH01 대비 새롭게 배우는 점
- 실제 소스 근거(파일/함수/행 번호)
- 기대되는 정상 동작과 변경 후 관찰 결과
- 실험 성공 판정 기준(가능하면 정량적인 지표)
- 예상 실패 원인·제약·복구 방법
- 추후 방어 코드 실험 아이디어(개념 수준)

### D. 최종 1순위 결론

**초심자가 첫 DLL Injection 실험을 수행한다는 전제**에서 가장 적합한 후보를 하나 고르고, 다른 후보보다 적합한 이유를 5~8문장으로 설명한다.

## 7. 작업 제한

- **이번 요청에서는 분석 보고만 작성한다.** 인젝션/후킹 구현, DLL 프로젝트 생성, 바이너리 패치, 메모리 수정, 빌드/실행은 하지 않는다.
- 확인되지 않은 주소, RVA, 오프셋, 호출 규약, 함수 위치를 추측으로 단정하지 않는다.
- 타사 프로그램의 보안 기능 우회·은닉·권한 상승·지속성 확보는 범위에서 제외한다.
- 게임 코드 수정 없이 가능한 후보와 사전 계측용 코드 변경이 필요한 후보를 구별한다.
- 필요하면 추가 확인이 필요한 코드 위치를 적되, 현재 파악된 내용만으로 후보 순위를 매긴다.
- 답변은 **한국어**, 간결하지만 근거가 드러나는 형태로 작성한다.

## 8. 결과물

분석 결과를 `docs/DLL_INJECTION_후보_분석.md`에 저장하고, 마지막에 **1순위 후보 / 근거 / 다음 실험에서 확인할 사항**을 3줄 이내로 요약하라. 이 문서 이외의 파일을 수정하지 않는다.
